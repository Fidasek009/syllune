# Engineering baseline

This documents the extension's architecture and implementation. Release acceptance is tracked separately. See [acceptance status](feasibility-status.md) for measured results and open gates, and [research](research.md) for dated source material.

## Toolchain

Dependency cooldown (verified 2026-11-05): Dependabot waits one day for both Bun and GitHub Actions version updates. Bun's `minimumReleaseAge = 86400` filters new direct and transitive resolutions. Because [Bun preserves locked versions](https://bun.sh/docs/pm/cli/install#minimum-release-age), the local [install scanner](https://bun.sh/docs/pm/security-scanner-api) also verifies npm publication timestamps before installation, including frozen installs. Exactly 24 hours is allowed; younger releases, missing timestamps, registry failures, and non-public-npm sources stop installation. This adds registry metadata requests even for cached/frozen installs, so dependency installation requires network access. It does not affect extension runtime or offline speech. No additional scanner package is installed.

[Dependabot cooldown excludes security updates](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference#cooldown): those PRs can still appear immediately, but their Bun installs must pass the same age check before CI succeeds. GitHub Actions cooldown is enforced by Dependabot, not Bun. Keep the scanner source in reviewer archives; do not bypass it to make an update green.

Use WXT 0.21.5, strict TypeScript, explicit Manifest V3 builds for Chrome and Firefox, and Bun 1.4.4 for package management, scripts, tests, native checking, and formatting. Keep a single frozen Bun lockfile. Browser code must not depend on development-only Bun APIs. Relevant upstream guidance: [WXT project structure](https://wxt.dev/guide/essentials/project-structure.html), [browser targets](https://wxt.dev/guide/essentials/target-different-browsers.html), [Bun checking](https://bun.com/docs/runtime/check), and [Bun formatting](https://bun.com/docs/format).

`bun run typecheck` checks page, worker, tool, and test environments; `bun run test` runs the product tests in `tests/`. `bun run format:check` checks repository formatting. Build the two browser targets with `bun run build` and `bun run build:firefox`.

## Product architecture

The context menus invoke selection or article reading. Web pages host a compact extension iframe; the source content script retains text-to-DOM mappings. A separate extension tab renders PDFs through bundled PDF.js, keeps the original tab, and creates page geometry in order while extracting page text on demand and caching it. A whole-PDF read builds the complete text only when requested, yielding between pages. A native-viewer selection is located by canonical page text as pages arrive. The player opens only after the matched span is sliced, normalized, and rendered as a text layer, and it speaks that same span while highlighting it. Selections made in the reader map through their page text nodes directly, and a text layer that finishes rendering under an active drag restores the selection end at the pointer instead of leaving it at the top of that page. Loaded PDF readers receive typed, addressed runtime commands. A shared source-session owner and command dispatcher keep selection, highlight, resize, and close semantics consistent across web and PDF adapters. Stored native-viewer selections are a one-time handoff, not a command mailbox. Site-specific access can be requested after a PDF fetch fails, using an explicit user gesture and optional host permissions. Sources: [PDF.js API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html), [Chrome permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions), and [Mozilla optional host permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/optional_host_permissions).

The playback bar provides sentence navigation, voice, speed, volume, and close. Speed and volume use native floating popovers. Volume applies a perceptual curve to the native audio element, while speed updates active and preloaded audio playback rates with pitch preservation enabled, without restarting synthesis. Voice, speed, and volume stay usable while a voice prepares: a slow or stuck load can be replaced by choosing another voice, which abandons the pending preparation and loads the new one. A testable playback controller owns the reading scope, discriminated phase, read-ahead, cancellation, voice preparation, and failure recovery. The entrypoint binds browser controls and preferences; a native-audio adapter owns clip media elements and their playback clock. Selection replaces the reading scope; sentence navigation must not leave it. Preparing a new source drops the previous scope, so a failed re-initialization asks for a fresh selection instead of replaying text that no longer maps to the page. PDF line-ending normalization preserves mappings to printed source fragments and leaves real inline compounds and domain dots intact.

The player's [Media Session](https://developer.mozilla.org/en-US/docs/Web/API/MediaSession) handlers map play/pause to playback, previous/next track to sentence navigation, and stop to closing the reader. Speech plays from explicitly revoked, local WAV blob URLs through media elements because [Firefox does not reliably activate OS media controls for Web Audio alone](https://bugzilla.mozilla.org/show_bug.cgi?id=2067534). No extra UI, permission, network request, or silent placeholder audio is used. Upcoming clips are preloaded; word synchronization uses the playing element’s media clock. File-backed chunk handoff uses ended events rather than sample-accurate Web Audio scheduling, so continuity remains an acceptance concern. Closing the reader removes handlers, stops playback, and revokes clip URLs. Firefox probes additionally exercise the native media-control service; physical keyboard/headset routing and OS arbitration still need device validation.

The speech path uses pinned Piper model data, ONNX Runtime Web, and Spellophone/eSpeak NG. Model files and configs are explicitly downloaded, integrity-checked, and stored locally; previews are requested only by deliberate action. The packaged eSpeak data inventory is renamed to `data-index.json` so the archive contains exactly one root `manifest.json`. The extension requests unlimited and persistent storage for downloaded voices; [Chrome documents](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies) its eviction protection, and one Firefox probe reported persistent storage after a download. The application source is MIT, while third-party code and data have separate terms. See [licensing](licensing.md) and [NOTICE](../NOTICE.md). Catalog inclusion alone does not establish voice licensing or quality.

Voice preparation identifies the unique duration operator, validates the decoder upsampling structure and 256-sample hop, and merges duplicate deterministic ONNX operations. It does not depend on exporter-specific node names, which the [ONNX IR specification](https://onnx.ai/onnx/repo-docs/IR.html) makes optional. Preview production exercises the shared speech path across the full catalog; its [coverage report](../voice-previews/README.md) retains per-model runtime failures rather than claiming catalog-wide compatibility from English/Czech fixtures.

A packaged worker synthesizes locally. Chrome uses an offscreen document coordinated through its extension service worker, with the player connected directly to that document; Firefox runs its worker from the extension background page. Audio remains in the reading tab, allowing tab switches while source navigation/closure ends the session. Read-ahead and generation identifiers reject stale results; active inference cancellation still requires scrutiny. The shared port registry validates client requests on both browsers. Open player ports retain the model; one host-lifetime deadline starts after the last disconnect, disposing the Firefox model or closing the Chrome document after two minutes. SpeechService has no independent retention timer. A short preparation lease and shared lifecycle lock protect the asynchronous gap before a new player port connects. `bun run probe:host` exercises this using shortened deadlines in a copied test bundle; `HOST_LIFECYCLE_REAL_TIME=1` uses production deadlines. PCM uses structured-clone messages in Firefox and Base64 in Chrome, where compatibility extends before the [Chrome 148 opt-in](https://developer.chrome.com/blog/structured-clone-messaging). See [Chrome offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen) and [Mozilla background scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts).

The CPU worker configures up to four threads only in a cross-origin-isolated context and otherwise configures one. The diagnostic records configured threads, not independent proof of actual thread use. Firefox extension pages currently lack SharedArrayBuffer support, so its CPU path remains single-threaded; see [Mozilla 1673477](https://bugzilla.mozilla.org/show_bug.cgi?id=1673477) and [Mozilla 2019902](https://bugzilla.mozilla.org/show_bug.cgi?id=2019902). Two- and three-thread target-device tuning remains unmeasured. CPU worker startup overlaps the local model read. When GPU availability resolves before that read finishes, both workers prepare the same model and compete to produce the first valid clip. They share one IndexedDB lookup. Legacy ArrayBuffers require a copy for the second worker. New downloads use IndexedDB Blobs, which both workers can read while pronunciation and GPU initialization run. The engine closes the slower worker and reuses the winner for later clips. The GPU worker retains model bytes so a later inference failure can transfer them to the CPU worker. A hard worker crash can still require a reread. Browser API presence is not evidence of correct or fast hardware inference. See [ONNX Runtime thread requirements](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html). The CPU session uses parallel execution mode and skips graph optimization. In the pinned ONNX Runtime, parallel mode cuts the time spent planning allocations, including in Firefox with one WASM thread. The WebGPU session uses full graph optimization. Both disable weight prepacking. The GPU adapter request overlaps phonemizer initialization. Successful GPU loads record adapter time separately from session creation.

On 2026-11-20, a Linux Zen 1.24b extension probe reached the native `playing` event in 1.30 s, down from 3.35 s, for a cold Cori Medium selection using one CPU thread. A Chrome 159 extension probe reached the native `playing` event in 1.58 s, down from 3.30 s, for a cold Cori Medium selection with CPU fallback. Two runs per configuration of the packaged worker measured median time from model transfer to first PCM. In Chrome, Cori Medium improved from 2.57 s to 0.72 s and Cori High from 3.25 s to 1.45 s. In Firefox 159, Kasandra Medium improved from 3.21 s to 1.17 s. Those worker measurements start with model bytes in memory. The Chrome CPU worker generated two clips per voice across all 171 available models, using local model and config files verified against the catalog hashes. A 40-word Cori Medium passage with synthesis noise set to zero produced identical word timings and a maximum absolute PCM sample difference below 0.000019. The test host has a virtual display adapter. SwiftShader experiments showed no comparable gain in WebGPU session creation. RTX hardware latency remains unmeasured.

GPU load and first inference retain separate three-second deadlines. CPU playback can start before either deadline expires. A CPU win records `cpu-first-clip` if the GPU has yet to return a clip or report a failure. GPU failures and timeouts disable further GPU attempts for the browser session. Later clips from a working GPU worker keep the normal request deadline.

A Linux Zen 1.24b test copy with a simulated GPU load stall reached Cori High playback in 4.79 s, down from 9.68 s with serial fallback. A simulated first-inference stall reached playback in 5.09 s, down from 8.81 s. Both pairs used the actual CPU worker and the native `playing` event. A rebuild after changes to the engine reached playback in 4.59 s with a simulated GPU load stall. A separate Cori High worker experiment split the ONNX graph before the vocoder. For one short English phrase, the encoder took 145–173 ms and the vocoder took 3.69–3.82 s on one thread. A separate eight-worker probe decoded overlapping time windows and trimmed each window to the samples it owned. The encoder and parallel decoder took 1.15–1.28 s together after loading. Across two clips, the maximum absolute difference from serial decoding of the same latent input was below 0.000001. The decoder workers alone took 1.15 s to prepare. In a subsequent warm run, the first partition became available after 0.92 s. Starting playback at that point would have left a calculated 45 ms gap before a later partition. The prototype ran only in the benchmark. RTX 3070 Ti latency remains unmeasured.

A paired Chromium CPU-worker run used one short localized phrase per voice and verified source files against the catalog hashes. All 171 available voices produced PCM with both session configurations. The revised setup generated the first PCM sooner in 128 pairs on the first pass, with a median 3.19× improvement in transfer-to-PCM time. All 43 remaining voices were faster on a second pass with the order reversed. These single-pair timings varied across runs. The test starts with model bytes in memory and excludes storage, player setup, and audio output.

On 2026-11-20, a Zen 1.24b storage probe measured seven reads of the 114 MB Cori High model. Median IndexedDB-to-buffer time was 377 ms with an ArrayBuffer record and 179 ms with a Blob. The rebuilt engine plays both record formats. A separate Zen worker probe used the same Cori High input with synthesis noise set to zero. Merging duplicate operations reduced the graph from 6,554 to 3,479 nodes. Median worker setup fell from 529 ms to 392 ms across two runs per condition. A Chromium CPU-worker comparison reproduced the original PCM and word timings for one short phrase per voice across all 171 available voices, with synthesis noise set to zero. The storage and graph changes apply when a voice is downloaded and prepared. Packaged-browser probes reached the native playing event in 3.96 s for cold Cori High in Zen with a simulated GPU load stall, and in 1.05 s for cold Cori Medium in Chrome with CPU fallback. Those runs used different voices and fallbacks, so they do not compare the browsers.

A matched comparison on 2026-11-21 used the same instrumented Cori model bytes, worker bundle, 110-character text and CPU backend inside each browser's extension page. Firefox 159 exposed no `SharedArrayBuffer` (`crossOriginIsolated` false; a `SharedArrayBuffer` postMessage was rejected), so ONNX Runtime fell back to one thread even when the worker requested four. Chromium is cross-origin isolated through its manifest COOP/COEP values and ran four threads. Cori Medium produced its first clip in 1.50–1.58 s in Zen and 0.76–0.95 s in Chromium; Cori High took 9.9–10.9 s and 3.0–3.3 s. Chromium forced to one thread took 1.70–1.72 s and 10.1–10.2 s, matching Zen within run-to-run variation. Per-thread speed is equivalent, and thread count accounts for the gap. Firefox ignored the same COOP/COEP values, and Firefox 159 on Linux had no `navigator.gpu`, so WebAssembly threads and WebGPU are both unavailable there.

Firefox compensates by splitting the instrumented voice at its first transposed convolution and decoding overlapping latent windows in separate one-thread workers. Each window carries 13 latent frames of context on both sides, the encoder and flow stay on one thread, and each window waits only for its own worker, so the vocoder pool does not delay the load response. Vocoders above 24 MB (13 of 171 voices) use up to four workers; smaller ones use two, where a wider pool's startup cost outweighs its decoding gain. With a 48-character first clip on the same Linux machine, Cori High's first audio fell from 7.6 s to 3.9 s and later clips from 7.4 s to 3.0 s. Cori Medium stayed at 1.8–1.9 s for the first clip and improved from 0.8 s to 0.6 s for later clips. A packaged Zen probe with a simulated GPU stall reached the native playing event in 2.9–4.9 s against 4.8–5.6 s. The shared context adds 26 frames of work per window, so short clips gain less than long ones, and Chromium keeps its four threads in one worker instead.

A Chromium CPU comparison with synthesis noise at zero reproduced the one-thread samples and word timings exactly for all 171 available voices, using four vocoder workers and the same 48-character text.

Memory is dominated by ONNX Runtime rather than the file size. With Zen already open on the extension page at 1.24 GB RSS, one cold Cori High session (114 MB graph) added 0.61 GB at peak and 0.34 GB when steady on one thread, and 1.66 GB peak and 1.03 GB steady with four vocoder workers. Each extra worker costs about 0.19 GB steady for the 55 MB High vocoder, near three times the graph's weight bytes once the runtime's own copy and allocator slack are included; two workers added 0.65 GB steady. Disabling the CPU memory arena, memory patterns or parallel execution mode did not change these figures. The four-core target runs three workers.

In a Chromium software WebGPU probe, the ONNX Runtime JSPI build reduced median Cori High worker setup from 3.58 s to 2.22 s. For one short Cori Medium phrase, time from model transfer to first PCM fell from 16.33 s to 14.58 s. The packaged build still uses Asyncify. The probe used SwiftShader and provides no physical GPU latency measurement.

Multi-speaker models read with their first speaker; the app exposes one voice per model, matching the speaker-zero previews. Speech messages carry no speaker choice.

Word highlighting derives timing from predicted acoustic frames and maps it to the original source. Source-specific phonemizer failures may be isolated through bounded recovery; runtime failures and cancellation must not silently discard content. Model and bounded speech caches must not persist reading text in diagnostics or analytics. Diagnostic transport and persistence use explicit metadata/timing allowlists; raw runtime errors and arbitrary strings are excluded. First-buffer readiness and first-audio readiness are distinct: the latter is stamped at the native media element’s `playing` event. Initial timing includes document/preference/voice preparation. Neither metric measures the physical speaker output. The first speech chunk targets 48 characters, preserving longer words within the normal 240-character limit. Target-device latency and listening quality remain open.

## Security and accessibility

Bundle executable code and use the extension CSP; user-selected PDF origins and explicit voice downloads are the network exceptions. Keep permissions narrow, validate cross-boundary messages, treat source content as untrusted, and avoid reading text in logs. Follow [Chrome remote-code guidance](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code), [Mozilla extension policies](https://extensionworkshop.com/documentation/publish/add-on-policies/), and the applicable [WCAG 2.2](https://www.w3.org/TR/WCAG22/) criteria. Keyboard, focus, contrast and assistive-technology checks remain release gates.

## Evidence and limitations

The product probes share isolated extension-copy setup and Chromium launch policy. Each shared launcher closes its test browser and removes only its own profile directory; it never uses a personal profile. Browser fixture writes use the production voice-store schema and transaction helper; only test copies contain fixture modules. The product and PDF probes under `scripts/` exercise parts of actual Chrome/Firefox builds and the original MUNI thesis, with test instrumentation and grants. They do not establish native operating-system menu behavior, every browser version, Windows, physical GPU behavior, all-document reading fidelity, or audible latency on target hardware. See [acceptance status](feasibility-status.md) for exact scope.

Document routing reads `document.contentType` under the user action rather than guessing from URL suffixes. Protected viewers that block inspection open the extension reader, where PDF.js validates the fetched bytes; site access remains explicit when required. Unsupported HTML cannot execute in that reader. Local-file behavior and its browser-specific fallback are documented in [known issues](known-issues.md). Chrome and Firefox local-file fixtures use `PDF_LOCAL=1`; the dedicated PDF probe accepts `PDF_SOURCE_PATH` for extensionless endpoint tests.

PDF.js worker URLs are emitted as hashed assets by WXT/Vite, so the worker changes with its bundled API instead of using an unversioned manually copied URL.

A native PDF selection is only a locator. Syllune matches its printed span on a key that drops whitespace and hyphens, because Chrome and Firefox viewers copy line breaks, spacing around superscripts, and line-end hyphens differently. The key retains raw offsets for every character, including ligatures and composed accents, then slices and normalizes that printed span. A match that starts or ends inside a printed word is rejected. When normalizing the span, a line-end hyphen before a lowercase continuation is layout hyphenation and is removed; a capital continuation or an already hyphenated word keeps the hyphen. The player speaks and highlights the same document, so a handoff cannot start audio before its mapping exists or speak text it cannot highlight. Native handoffs use the first matching key; selecting inside the reader chooses the exact occurrence.
