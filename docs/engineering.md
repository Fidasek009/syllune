# Engineering baseline

This documents the extension's architecture and implementation. Release acceptance is tracked separately. See [acceptance status](feasibility-status.md) for measured results and open gates, and [research](research.md) for dated source material.

## Toolchain

Dependency cooldown (verified 2026-11-05): Dependabot waits one day for both Bun and GitHub Actions version updates. Bun's `minimumReleaseAge = 86400` filters new direct and transitive resolutions. Because [Bun preserves locked versions](https://bun.sh/docs/pm/cli/install#minimum-release-age), the local [install scanner](https://bun.sh/docs/pm/security-scanner-api) also verifies npm publication timestamps before installation, including frozen installs. Exactly 24 hours is allowed; younger releases, missing timestamps, registry failures, and non-public-npm sources stop installation. This adds registry metadata requests even for cached/frozen installs, so dependency installation requires network access. It does not affect extension runtime or offline speech. No additional scanner package is installed.

[Dependabot cooldown excludes security updates](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference#cooldown): those PRs can still appear immediately, but their Bun installs must pass the same age check before CI succeeds. GitHub Actions cooldown is enforced by Dependabot, not Bun. Keep the scanner source in reviewer archives; do not bypass it to make an update green.

Use WXT 0.21.5, strict TypeScript, explicit Manifest V3 builds for Chrome and Firefox, and Bun 1.4.4 for package management, scripts, tests, native checking, and formatting. Keep a single frozen Bun lockfile. Browser code must not depend on development-only Bun APIs. Relevant upstream guidance: [WXT project structure](https://wxt.dev/guide/essentials/project-structure.html), [browser targets](https://wxt.dev/guide/essentials/target-different-browsers.html), [Bun checking](https://bun.com/docs/runtime/check), and [Bun formatting](https://bun.com/docs/format).

`bun run typecheck` checks page, worker, tool, and test environments; `bun run test` runs the product tests in `tests/`. `bun run format:check` checks repository formatting. Build the two browser targets with `bun run build` and `bun run build:firefox`.

## Product architecture

The context menus invoke selection or article reading. Web pages host a compact extension iframe; the source content script retains text-to-DOM mappings. A separate extension tab renders PDFs through bundled PDF.js, retains source offsets, and prepares visible canvas/text layers on demand. Loaded PDF readers receive typed, addressed runtime commands. A shared source-session owner and command dispatcher keep selection, highlight, resize, and close semantics consistent across web and PDF adapters. Stored native-viewer selections are a one-time handoff, not a command mailbox. PDF text extraction and native-viewer handoff remain performance and correctness concerns; see the acceptance status. Site-specific access can be requested after a PDF fetch fails, using an explicit user gesture and optional host permissions. Sources: [PDF.js API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html), [Chrome permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions), and [Mozilla optional host permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/optional_host_permissions).

The playback bar provides sentence navigation, voice, speed, volume, and close. Speed and volume use native floating popovers. Volume applies a perceptual curve to the native audio element, while speed updates active and preloaded audio playback rates with pitch preservation enabled, without restarting synthesis. A testable playback controller owns the reading scope, discriminated phase, read-ahead, cancellation, voice preparation, and failure recovery. The entrypoint binds browser controls and preferences; a native-audio adapter owns clip media elements and their playback clock. Selection replaces the reading scope; sentence navigation must not leave it. PDF line-ending normalization preserves mappings to printed source fragments and leaves real inline compounds and domain dots intact.

The player's [Media Session](https://developer.mozilla.org/en-US/docs/Web/API/MediaSession) handlers map play/pause to playback, previous/next track to sentence navigation, and stop to closing the reader. Speech plays from explicitly revoked, local WAV blob URLs through media elements because [Firefox does not reliably activate OS media controls for Web Audio alone](https://bugzilla.mozilla.org/show_bug.cgi?id=2067534). No extra UI, permission, network request, or silent placeholder audio is used. Upcoming clips are preloaded; word synchronization uses the playing element’s media clock. File-backed chunk handoff uses ended events rather than sample-accurate Web Audio scheduling, so continuity remains an acceptance concern. Closing the reader removes handlers, stops playback, and revokes clip URLs. Firefox probes additionally exercise the native media-control service; physical keyboard/headset routing and OS arbitration still need device validation.

The speech path uses pinned Piper model data, ONNX Runtime Web, and Spellophone/eSpeak NG. Model files and configs are explicitly downloaded, integrity-checked, and stored locally; previews are requested only by deliberate action. The packaged eSpeak data inventory is renamed to `data-index.json` so the archive contains exactly one root `manifest.json`. The extension requests unlimited and persistent storage for downloaded voices; [Chrome documents](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies) its eviction protection, and one Firefox probe reported persistent storage after a download. The application source is MIT, while third-party code and data have separate terms. See [licensing](licensing.md) and [NOTICE](../NOTICE.md). Catalog inclusion alone does not establish voice licensing or quality.

Timing instrumentation identifies the unique duration operator and validates the decoder upsampling structure and 256-sample hop. It does not depend on exporter-specific node names, which the [ONNX IR specification](https://onnx.ai/onnx/repo-docs/IR.html) makes optional. Preview production exercises the shared speech path across the full catalog; its [coverage report](../voice-previews/README.md) retains per-model runtime failures rather than claiming catalog-wide compatibility from English/Czech fixtures.

A packaged worker synthesizes locally. Chrome uses an offscreen document coordinated through its extension service worker, with the player connected directly to that document; Firefox runs its worker from the extension background page. Audio remains in the reading tab, allowing tab switches while source navigation/closure ends the session. Read-ahead and generation identifiers reject stale results; active inference cancellation still requires scrutiny. The shared port registry validates client requests on both browsers. Open player ports retain the model; one host-lifetime deadline starts after the last disconnect, disposing the Firefox model or closing the Chrome document after two minutes. SpeechService has no independent retention timer. A short preparation lease and shared lifecycle lock protect the asynchronous gap before a new player port connects. `bun run probe:host` exercises this using shortened deadlines in a copied test bundle; `HOST_LIFECYCLE_REAL_TIME=1` uses production deadlines. PCM uses structured-clone messages in Firefox and Base64 in Chrome, where compatibility extends before the [Chrome 148 opt-in](https://developer.chrome.com/blog/structured-clone-messaging). See [Chrome offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen) and [Mozilla background scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts).

The CPU worker configures up to four threads only in a cross-origin-isolated context and otherwise configures one. The diagnostic records configured threads, not independent proof of actual thread use. Firefox extension pages currently lack SharedArrayBuffer support, so its CPU path remains single-threaded; see [Mozilla 1673477](https://bugzilla.mozilla.org/show_bug.cgi?id=1673477) and [Mozilla 2019902](https://bugzilla.mozilla.org/show_bug.cgi?id=2019902). Two- and three-thread target-device tuning remains unmeasured. GPU initialization and inference have a CPU fallback. The GPU worker retains recoverable model bytes so inference failure can transfer them to the CPU worker without another IndexedDB read; this costs an additional model-sized buffer while using the GPU. A failed GPU provider is remembered for the browser session. Worker script parsing and static runtime imports overlap the model read; ORT WASM initialization still begins at session creation. A hard worker crash cannot return the transferred buffer and can still require a reread. Browser API presence is not evidence of correct or fast hardware inference. See [ONNX Runtime thread requirements](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html). Production uses full graph optimization with prepacking disabled, which loaded fastest in four rotated rounds on the Chrome test VM. This is evidence for the tested model/device, not an optimum across voices, devices, or Firefox.

Multi-speaker models read with their first speaker; the app exposes one voice per model, matching the speaker-zero previews. Speech messages carry no speaker choice.

Word highlighting derives timing from predicted acoustic frames and maps it to the original source. Source-specific phonemizer failures may be isolated through bounded recovery; runtime failures and cancellation must not silently discard content. Model and bounded speech caches must not persist reading text in diagnostics or analytics. Diagnostic transport and persistence use explicit metadata/timing allowlists; raw runtime errors and arbitrary strings are excluded. First-buffer readiness and first-audio readiness are distinct: the latter is stamped at the native media element’s `playing` event. Initial timing includes document/preference/voice preparation. Neither metric measures the physical speaker output. The first speech chunk targets 48 characters, preserving longer words within the normal 240-character limit. Target-device latency and listening quality remain open.

## Security and accessibility

Bundle executable code and use the extension CSP; user-selected PDF origins and explicit voice downloads are the network exceptions. Keep permissions narrow, validate cross-boundary messages, treat source content as untrusted, and avoid reading text in logs. Follow [Chrome remote-code guidance](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code), [Mozilla extension policies](https://extensionworkshop.com/documentation/publish/add-on-policies/), and the applicable [WCAG 2.2](https://www.w3.org/TR/WCAG22/) criteria. Keyboard, focus, contrast and assistive-technology checks remain release gates.

## Evidence and limitations

The product probes share isolated extension-copy setup and Chromium launch policy. Each shared launcher closes its test browser and removes only its own profile directory; it never uses a personal profile. Browser fixture writes use the production voice-store schema and transaction helper; only test copies contain fixture modules. The product and PDF probes under `scripts/` exercise parts of actual Chrome/Firefox builds and the original MUNI thesis, with test instrumentation and grants. They do not establish native operating-system menu behavior, every browser version, Windows, physical GPU behavior, all-document reading fidelity, or audible latency on target hardware. See [acceptance status](feasibility-status.md) for exact scope.

Document routing reads `document.contentType` under the user action rather than guessing from URL suffixes. Protected viewers that block inspection open the extension reader, where PDF.js validates the fetched bytes; site access remains explicit when required. Unsupported HTML cannot execute in that reader. Local-file behavior and its browser-specific fallback are documented in [known issues](known-issues.md). Chrome and Firefox local-file fixtures use `PDF_LOCAL=1`; the dedicated PDF probe accepts `PDF_SOURCE_PATH` for extensionless endpoint tests.

PDF.js worker URLs are emitted as hashed assets by WXT/Vite, so the worker changes with its bundled API instead of using an unversioned manually copied URL.

Native PDF handoff keeps the original speech text stable. A separate canonical offset projection maps words to extracted PDF runs across layout whitespace, line-wrap joins, ligatures and composed/decomposed accents. Mapping does not require byte-identical source strings or replace the text during playback. The last highlight is reapplied when indexing finishes. Ambiguous matches remain rejected.
